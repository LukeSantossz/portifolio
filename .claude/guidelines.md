# Project guidelines — Portfolio

Best-practice conventions for this repository. These are versioned (committed)
so every contributor — human or AI — works the same way. Personal overrides go
in `.claude/settings.local.json`, which stays git-ignored.

## What this project is

A static, single-page Astro portfolio that frames each project as a business
case study (problem → approach → result). It compiles to fully pre-rendered
HTML and deploys to Vercel. The only runtime call is the client-side `fetch` to
Web3Forms from the contact form.

- **Framework:** Astro 6, `output: 'static'`
- **Styling:** Tailwind CSS v4, wired through PostCSS (`postcss.config.mjs`), not
  the `@tailwindcss/vite` plugin — Astro 6's Rolldown-based Vite breaks with the
  plugin. Do not switch this back.
- **Language:** TypeScript (`strict`, via `astro/tsconfigs/strict`).

## Golden rule: content is decoupled from rendering

Components never hold copy. All text, metrics, links and identity live in data:

- `src/data/site.ts` — identity, contact, SEO, hero stats, integration keys.
- `src/data/skills.ts` — skill groups.
- `src/data/experience.ts` — work/education timeline.
- `src/content/projects/*.md` — one Markdown file per project, validated against
  the Zod schema in `src/content.config.ts`.

When asked to "update a project / skill / metric", edit the data or Markdown —
**do not** hard-code strings inside `.astro` components.

## Directory layout

```
src/
├── components/
│   ├── sections/   # full page sections (Hero, About, Services, Skills,
│   │               # Projects, Experience, Contact) — one per scroll block
│   ├── ui/         # reusable building blocks (Icon, SocialLinks, ProjectCard)
│   └── layout/     # site chrome (Nav, Footer)
├── content/projects/  # case-study Markdown (schema-validated)
├── data/              # typed content (site, skills, experience)
├── layouts/           # Layout.astro (the single HTML shell)
├── pages/             # index.astro (single entry point)
└── styles/            # global.css (Tailwind v4 @theme tokens + custom CSS)
public/                # static assets served as-is (résumé, favicon, robots, OG)
```

Place new files by role: a new page block → `sections/`; a reusable widget →
`ui/`; navigation/footer chrome → `layout/`. Keep components small and focused.

### Import paths after the grouping

- `sections/*` and `layout/*` reach data with `../../data/...` and reach UI
  building blocks with `../ui/...`.
- `ui/*` components import siblings with `./...` and data with `../../data/...`.
- `src/pages/index.astro` imports `../components/<group>/<Name>.astro`.

## Styling conventions

- Use the design tokens defined in `src/styles/global.css` under `@theme`
  (`--color-accent`, `--color-ink`, `--font-mono`, …). Tailwind v4 exposes them
  as utilities (`bg-accent`, `text-ink`, …). Add a token rather than hard-coding
  a hex value when a color is reused.
- The accent palette is grass green (`--color-accent`) + harvest gold
  (`--color-accent-2`) — the agribusiness theme. Stay within it.
- Prefer Tailwind utility classes in markup; reserve `global.css` for tokens,
  keyframes, and component patterns that utilities can't express cleanly
  (marquee, the projects deck, reveal animations).

## Accessibility

This is a baseline, not a nice-to-have. Preserve it when editing:

- Every icon-only control has an `aria-label`; decorative elements use
  `aria-hidden`.
- Interactive widgets keep their roles/state (`role="tab"`, `aria-selected`,
  `inert` on inactive deck cards, `aria-live` on the form status).
- Keep the skip-link (`Layout.astro`) and visible focus styles.
- Any new animation must respect `prefers-reduced-motion` (see `global.css`).

## How to add a project

1. Create `src/content/projects/<slug>.md`.
2. Fill the frontmatter required by `src/content.config.ts`: `title`, `tagline`,
   `problem`, `approach`, `result`, `stack` (plus optional `domain`, `roadmap`,
   `image`, `repoUrl`, `demoUrl`, `period`, `featured`, `order`).
3. Cards sort by `featured` first, then ascending `order`.
4. For a banner, drop an image in `public/images/projects/` and set
   `image: "/images/projects/<file>"`; otherwise a gradient monogram is generated.

## Working norms

- **Evaluate before modifying.** Read the affected component/data and match the
  surrounding style (comment density, naming, idiom) before changing it.
- **Build must pass before committing:** run `npm run build`. There is no test
  suite — the build and manual review are the safety net.
- **Commits:** concise, imperative subject lines describing the change. No
  co-author / "generated by" trailers.
- **Keep docs in sync:** if you change the directory layout or commands, update
  this file and the README's "Project Structure" section in the same change.

## Commands

```bash
npm run dev      # dev server at http://localhost:4321
npm run build    # static bundle in /dist (use this to verify changes)
npm run preview  # serve the production build locally
```
