problem: "Sentiment analysis means automatically judging the feeling behind a piece of text. The catch is that most ready-made tools are trained on clean, formal writing and quietly fall apart on tweets, where slang, mentions, hashtags and emojis break the assumptions they were built on. I set out to fine-tune a language model for exactly that informal, noisy text, and the first attempt failed in an interesting way."
constraints: "Any claim of improvement needed a measured starting point that was actually fair, not a number borrowed from someone else's published results. The cleaning of tweets had to be correct down to individual emojis, which are easy to corrupt when a program splits text the wrong way. And the preprocessing had to be fast enough to handle a million tweets, not just a small sample."
approach: "I started from RoBERTa, a language model for understanding text, in a version already specialized for Twitter, and fine-tuned it. It came out worse than where it started, scoring 2.72 percent lower than the baseline. Rather than tuning settings until the number moved, I did an error analysis broken down by category and found the cause: the starting model had already been trained on this exact task, so training it again on the same data only made it overfit. I wrote that finding down as a decision record with five alternatives and their reasons for rejection, then switched to a task-agnostic starting model and a different classification task. Separately, because the Python cleaning step is the bottleneck at large volumes, I rebuilt it in Rust, a language known for speed and safety, and proved it produces the same output as the original."
alternatives: "The tempting move after a bad result is to keep adjusting the learning rate and batch size until something improves, but that treats a structural problem as a tuning problem and would have burned days. Comparing against the starting model's own published score was the other shortcut, and I rejected it because a score published by the model's authors is not a baseline you earned; the honest comparison is a simple classifier trained on the frozen model's features, which is what I used."
result: "After the pivot, the fine-tuned model reaches 0.887 macro F1 against a frozen-features baseline at 0.584, a 51.9 percent relative gain, with the largest improvements on the rarest categories. Macro F1 is an accuracy measure where 1.0 is perfect and every category counts equally, regardless of how often it appears. The effect of balancing rare categories was reported as a controlled experiment with and without, not assumed. The Rust cleaning tool runs 28.5 times faster than the Python version on a million rows, 33.1 seconds down to 1.2, with output parity checked at three different sizes. The failed run is kept under a release tag rather than deleted."
evaluation: "The comparison is against a baseline trained on the frozen model's features, not against the score the starting model's authors published, because a published score is not a baseline this project earned. Macro-F1 weights every category equally regardless of how often it appears, which is why the gain concentrates in the rarest ones. The class-balancing effect was run with and without rather than assumed, and the Rust parity check compares output at three input sizes rather than at one."
retrospective: "The first attempt is the most useful part of this project, and I left it visible on purpose. I also retired the older speed figures from the documentation once a change to the cleaning contract made them no longer apply, rather than leaving a flattering number in place that the code no longer earned. The training outputs are not committed, so the reported scores rest on the recorded runs rather than on artifacts a reader can re-open."
