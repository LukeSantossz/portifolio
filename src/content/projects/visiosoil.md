problem: "A soil's texture is its mix of sand, silt and clay, and it drives real decisions about irrigation and planting. Reading it normally means sending a sample to a lab or calling in a specialist, and on a large farm with no phone signal neither of those happens, so most fields are never assessed at all. VisioSoil classifies soil texture from a single photo, right on the phone."
constraints: "It had to work with no internet whatsoever, because that is exactly where it is needed. It had to fit and run on an ordinary phone rather than a server. And the reading had to be trustworthy, since a soil measurement is only useful if you also know exactly where it was taken and whether the photo was good enough to judge."
approach: "The image model runs fully on the device using TensorFlow Lite, which is Google's tool for running models on phones, on a compact network called MobileNetV2 that is light enough for mobile hardware. Classification runs in its own background worker that a timeout can actually terminate, rather than one left holding the hardware after the app has stopped waiting for it. Every reading is saved on the phone with its GPS location, behind a storage layer that does not care whether the data later syncs to a server. On the data side, photos of the same physical soil sample are kept together so they cannot end up on both sides of a train and test split, and each split carries a checksum of the dataset it came from, so a split can be proven to belong to the data it claims."
alternatives: "The simpler path was a cloud service that does the classification on a server, but that fails the moment the signal drops, which is most of the time in the field. The other shortcut was to save readings straight into a fixed database. I put a storage abstraction in between instead, so adding optional cloud sync later does not mean rewriting the app. For the photo-quality check I could have written it once in the app, but the same rule has to govern which photos enter the dataset, so I wrote it in both languages and locked them to a shared reference file that fails both test suites if they ever disagree."
result: "The project placed 3rd out of more than 1,300 entries at the 16th FETEPS 2025, a large science and technology fair run by the São Paulo State technical school system, and the research paper was published and presented as a poster at the 17th International Conference on Precision Agriculture and the 11th ConBAP in Porto Alegre in July 2026. The app ships the complete offline loop of capture, classify and store. Along the way I found and fixed four real security defects, including GPS coordinates surviving inside photo metadata because a library flag is silently ignored on Android camera captures, and access tokens reaching device logs through how an error formats itself. The build pipeline runs six jobs, including one that unpacks the release app to prove the optimizer did not strip the authentication code and another that boots it on an emulator to catch crashes that only appear in the packaged build."
retrospective: "The model that won the competition is not the one shipped inside the app, and the app currently expects a different number of categories than the next model will produce, so wiring the production model in and letting it read its own labels at startup is the main open thread. I also audited the delivered photo archive and found it was not shot on a fixed rig as assumed, with scale varying by a factor of 2.6 across images, which retired one of my earlier design decisions outright. The storage abstraction already leaves room for the remote sync a multi-device rollout would need."
